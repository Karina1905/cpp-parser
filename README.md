# Синтаксичний аналізатор підмножини C++ (Flex + Bison)

Лабораторна робота. Зробила парсер для підмножини C++ на Flex/Bison, він будує AST,
по AST можна виконати програму (інтерпретатор), згенерувати код на Python і
подивитися дерево в браузері (d3.js).

## Структура

```
src/lexer.l      лексер (Flex)
src/parser.y     граматика + побудова AST (Bison)
src/ast.hpp      структура вузла дерева
src/json.cpp     вивід AST у JSON
src/sema.cpp     статичний семантичний аналіз
src/interp.cpp   інтерпретатор
src/codegen.cpp  генерація коду на Python
src/main.cpp     запуск з командного рядка
viz/index.html   візуалізація AST окремо (d3.js, без сервера)
web/             веб-playground: редактор, запуск, AST, Python
examples/        тестові програми
run_tests.sh     порівнює вивід інтерпретатора і згенерованого Python
```

## Як запустити

Потрібно: flex, bison 3.x, g++, python3.

```bash
make                  # збірка, з'являється ./cppparser
make demo             # розбір examples/shapes.cpp + запуск + Python + ast.js
make test             # всі приклади
make serve            # веб-playground на http://localhost:8000
```

Окремо:

```bash
./cppparser examples/shapes.cpp --run               # виконати
./cppparser examples/shapes.cpp --gen out/shapes.py # згенерувати Python
python3 out/shapes.py
./cppparser examples/shapes.cpp --print             # AST у JSON
./cppparser examples/shapes.cpp --viz viz/ast.js    # AST для браузера
./cppparser examples/bad.cpp                        # приклад помилки синтаксису
./cppparser examples/sema_errors.cpp                # приклад семантичних помилок (16 штук)
```

## Веб-playground

`make serve` і відкрити http://localhost:8000. Зліва редактор коду (можна вибрати
приклад або написати свій, поле stdin — для `cin`), кнопка «Виконати» або Cmd+Enter.
Справа вкладки:

- Вивід — результат інтерпретатора і згенерованого Python поряд, і чи збігаються;
- AST — інтерактивне дерево (d3.js): клік згортає/розгортає, зум колесом, при
  наведенні показує рядок у коді;
- Python — згенерований код, можна скопіювати чи завантажити;
- Повідомлення — помилки парсера, рядок з помилкою підсвічується в редакторі.

Сервер `web/server.py` — звичайний `http.server` зі стандартної бібліотеки, без
залежностей: приймає код, кладе в тимчасову папку, запускає `cppparser` і python3
з обмеженням 5 секунд, повертає JSON. d3.js лежить локально, інтернет не потрібен.

Є ще `viz/index.html` — та сама візуалізація AST без сервера: `./cppparser file.cpp --viz viz/ast.js`
і відкрити файл у браузері.

## Що підтримується

- типи int, double, bool, char, string, void, свої класи
- `#include`, `using namespace std;`, коментарі
- змінні `int a, b = 1;`, масиви `int a[5] = {1,2,3};`, об'єкти `Point p(1, 2);`
- функції, рекурсія, прототипи
- класи: поля, конструктори (можна кілька), списки ініціалізації `: Base(a), x(b)`,
  методи в класі і поза ним (`double Circle::area() {...}`), `this->`, спадкування,
  public/private
- if / else if / else, while, do-while, for, break, continue, return
- арифметика, порівняння, `&& || !`, `?:`, `+= -=` і т.д., `++ --`, `(int) x`,
  індексація, `.` і `->`, виклики
- `cout << ... << endl;`, `cin >> x;`, sqrt, pow, abs, max, min, `s.length()`

Не робила: вказівники, шаблони, new/delete, switch, посилання `int&` (у параметрах
приймається синтаксично, але працює як передача за значенням). Всі методи працюють
як virtual. Об'єкти копіюються при оголошенні, присвоєнні і передачі в функцію,
масиви передаються за посиланням (як у C++ після розпаду масиву у вказівник).
`P p();` трактується як прототип функції, а не об'єкт (most vexing parse, як у C++).
Порядок обчислення аргументів і `i++ + ++i` — зліва направо (у C++ це UB).
Переповнення int: інтерпретатор рахує у 64-бітних числах і переповнюється, Python —
ні, тому `2^70` дасть різний результат (у C++ це UB, тож це єдина відома
розбіжність між бекендами). Глибина рекурсії обмежена 50000 викликами.

## Як це працює

```
file.cpp -> lexer.l (токени) -> parser.y (AST) -> json.cpp   -> ast.json / ast.js -> браузер
                                              -> sema.cpp   -> список помилок (якщо є — стоп)
                                              -> interp.cpp -> виконання
                                              -> codegen.cpp -> out.py
```

AST — однакові вузли `Node { type, value, kids, line }`. Наприклад
`int f(int n) { return n * 2; }` стає
`FuncDecl("f")[ Type("int"), Params[Param("n")[Type("int")]], Block[Return[BinOp("*")[Ident("n"), IntLit("2")]]] ]`.

Лексер: регулярки -> токени, окремі стани для рядків і коментарів `/* */`,
`yylineno` для повідомлень про помилки.

Парсер: приблизно 90 правил, 302 стани, конфліктів немає. В діях правил тільки
будується дерево, вся семантика в окремих файлах.

Семантичний аналіз (`sema.cpp`): окремий прохід по AST до виконання. Спочатку
збирає класи (поля, методи, конструктори, базовий клас) і функції, потім
перевіряє кожну функцію зі стеком областей видимості. Для кожного виразу
виводить тип (`int`, `double`, `string`, ім'я класу, `int[]` ...). Ловить:
неоголошені змінні/функції/класи, повторні оголошення, невідомі типи, кількість
і типи аргументів, відсутній конструктор з такою кількістю аргументів, невідомі
поля й методи, несумісні типи в присвоєнні/ініціалізації/операціях (`int n = s`,
`s + 1`, `7.5 % 2`), присвоєння не-lvalue (`5 = a`), `break`/`continue` поза
циклом, `this` поза методом, `return` зі значенням у `void` і без значення в
не-`void`, функцію, яка може дійти до кінця без `return` (окрім `main`), метод
`Class::f` без прототипу в класі, відсутність `main`. Всі помилки збираються
в список, а не зупиняють на першій. `--no-sema` вимикає прохід.

Інтерпретатор: обходить дерево. `Value` — значення з тегом типу, `Env` — стек
областей видимості плюс `this` і глобальні змінні. break/continue/return зроблені
через винятки. При присвоєнні тип змінної зберігається (`int x = 7.9` дає 7).

Генератор Python: ділення і остача через `_div`/`_mod`, щоб було як у C
(`7/2 = 3`, `-7%3 = -1`); `cout` -> `print(..., sep="", end="")`; `for` -> `while`
(крок дублюється перед `continue`); `else if` -> `elif`; кілька конструкторів ->
`__init__(self, *args)` з перевіркою `len(args)`; поля в методах -> `self.x`;
якщо функція змінює глобальну змінну — додається `global x`.
Генератор веде стек областей видимості з типами змінних, тому:
- `{ int x = 3; }` всередині функції, де вже є `x`, стає `x_2` (у Python немає
  блокових областей);
- `int t = 7.9` -> `t = int(7.9)`, `bool ok = 5` -> `bool(5)`, параметри `double`
  приводяться на вході функції, `return` — до типу функції;
- `a = b = c` і `i++` всередині виразу -> оператор `:=` (walrus);
- масив об'єктів -> `[P() for _ in range(n)]`, а не `[P()] * n` (інакше всі
  елементи були б одним об'єктом);
- `char` у Python — рядок з одного символу, тому в арифметиці він обгортається в
  `_ord(c)`, а результат, що присвоюється в `char`, — в `_chr(...)`: `c + 1` -> 66,
  `c++` -> наступна літера, `(char)(c + 2)` -> `'C'`, порівняння `c == 'A'` лишаються
  рядковими.

## Теорія

### LALR(1)

LR-парсер читає вхід зліва направо і будує правий вивід у зворотному порядку
(знизу вгору). Є стек і дві дії: shift (покласти токен на стек) і reduce
(замінити праву частину правила на нетермінал). Стан автомата — набір пунктів
виду `A -> α • β`.

- LR(0) — без lookahead, майже завжди конфлікти.
- SLR(1) — reduce тільки якщо наступний токен є в FOLLOW(A). Простий, але FOLLOW
  грубий, бо рахується для всієї граматики.
- LR(1) — до кожного пункту додається lookahead. Найточніший, але станів дуже
  багато.
- LALR(1) — беремо LR(1) і зливаємо стани з однаковим ядром (однаковими пунктами
  без lookahead), lookahead-множини об'єднуються. Станів стільки ж, як у SLR, а
  точність майже як у LR(1). Мінус: при злитті можуть з'явитися нові reduce/reduce
  конфлікти (shift/reduce не з'являються). Bison будує LALR(1) за замовчуванням.

Таблиця парсера: `ACTION[стан, термінал]` = shift / reduce / accept / error і
`GOTO[стан, нетермінал]`. Усі стани є у файлі `build/parser.output` (після `bison -v`).

### Як працює yacc/Bison

1. Вхід — файл `.y`: токени (`%token`), пріоритети (`%left`, `%right`,
   `%nonassoc`), тип значень (`%union`), правила з діями, код на C/C++.
2. Bison додає правило `$accept -> program $end`, будує LR(0)-автомат, рахує
   lookahead, знаходить конфлікти, будує таблиці і генерує `parser.tab.cpp` з
   функцією `yyparse()`.
3. `yyparse()` в циклі дивиться `ACTION[стан, токен]`. Токени бере з `yylex()`
   (його генерує Flex), значення передаються через `yylval`, позиції через
   `yylloc`.
4. Дії виконуються на reduce: `$$` — значення лівої частини, `$1..$n` — правої.
   У мене всі дії будують вузли AST (`mk`, `mk1`, `mk2`, `list_append`).
5. При помилці викликається `yyerror()`. `%define parse.error verbose` дає
   повідомлення типу "unexpected X, expecting Y".

### Конфлікти

**Shift/reduce** — в одному стані можна і зсунути токен, і згорнути правило.
За замовчуванням Bison робить shift і пише попередження. Правильний спосіб —
пріоритети: токенам задаються пріоритет і асоціативність (чим нижче у файлі, тим
вищий), правило отримує пріоритет свого останнього терміналу або через `%prec`.
Якщо пріоритет токена вищий — shift, нижчий — reduce, рівні: `%left` -> reduce,
`%right` -> shift, `%nonassoc` -> помилка.

Приклади з моєї граматики:
- `expr '+' expr • '*'` — у `*` пріоритет вищий, тому shift, виходить `2 + (3*4)`.
  `expr '+' expr • '+'` — рівні і `%left`, тому reduce (ліва асоціативність).
  `a = b = c` — `%right`, shift.
- Dangling else: у стані `IF '(' expr ')' stmt •` при `ELSE` можна reduce (if без
  else) або shift. Я задала `%nonassoc LOWER_THAN_ELSE` нижче і `%nonassoc ELSE`
  вище, коротке правило має `%prec LOWER_THAN_ELSE`, тому ELSE зсувається і
  `else` прив'язується до найближчого `if`, як у C++. У `parser.output` це стан 277:
  `ELSE shift, and go to state 286; $default reduce`.
- `'-' expr • INC` — INC має вищий пріоритет за UMINUS, тому shift: `-a++` = `-(a++)`.

**Reduce/reduce** — два правила можна згорнути при одному lookahead. За замовчуванням
Bison бере те, що раніше в граматиці. Пріоритети тут не допомагають, треба
переписувати граматику. У мене такий конфлікт був: `Point p();` на верхньому
рівні — це об'єкт з порожніми аргументами (`args -> ε`) чи прототип функції
(`params -> ε`)? Після `'('` з lookahead `')'` незрозуміло, яке з двох порожніх
правил згортати. Це відомий у C++ "most vexing parse", стандарт каже, що
`T p();` — функція. Тому я зробила так, щоб для об'єкта список аргументів був
непорожній — конфлікт зник.

Знайти конфлікти можна через `bison -v` (файл `parser.output`) і
`bison -Wcounterexamples` (показує два варіанти розбору).

### Чому повний C++ не LALR(1)

`a * b;` — множення чи оголошення вказівника, залежить від того, чи `a` тип.
`A<B, C> d;` — шаблон чи два порівняння. Справжні компілятори (GCC, Clang) парсять
рекурсивним спуском з таблицею символів. Я прибрала вказівники і шаблони, а
`IDENT IDENT` (тип + змінна) автомат розрізняє сам: після IDENT, якщо далі IDENT —
це тип, інакше вираз.

## Можливі питання по коду

- Чому `strdup` у лексері? Flex перезаписує `yytext`, тому рядок треба скопіювати,
  парсер потім робить `free`.
- Як `int a, b = 1;` стає окремими вузлами? `attach_type()` копіює вузол типу в
  кожен декларатор. Якщо декларатор один — обгортка `Decls` не створюється.
- Де перевірка типів? Статично в `sema.cpp` (функція `expr` повертає тип виразу,
  `compatible` перевіряє сумісність) і ще раз динамічно в інтерпретаторі
  (`coerce`, `assign_to`), бо значення приводяться під час виконання.
- Чому семантика не в діях Bison? Щоб парсер лишався чистим синтаксисом: AST
  будується завжди, а перевірки й виконання — окремі проходи по готовому дереву.
  Так простіше показати AST навіть для програми з семантичними помилками.
- Як `return` виходить із вкладених циклів? Виняток `ReturnSignal`, його ловить
  `call_user`. `Block` при розкрутці прибирає свою область видимості.
- Чому в Python `for` стає `while`? Крок виконується в кінці тіла, а перед
  `continue` він вставляється окремо (стек `loopSteps`).
- Як шукається метод при спадкуванні? `find_method` іде по ланцюжку `base`
  від класу об'єкта, тому всі методи виходять віртуальними.
