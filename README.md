# Парсер підмножини C++ на Flex + Bison

Лабораторна робота №3, системне програмування.

Що зроблено:
- лексер (Flex) і синтаксичний аналізатор LALR(1) (Bison) для підмножини C++;
- побудова AST;
- статичний семантичний аналіз;
- інтерпретатор (виконання по AST);
- транслятор у Python;
- візуалізація AST у браузері (d3.js) і веб-playground.

## Структура

```
src/lexer.l      лексер
src/parser.y     граматика, побудова AST
src/ast.hpp      вузол AST
src/sema.cpp     семантичний аналіз
src/interp.cpp   інтерпретатор
src/codegen.cpp  генерація Python
src/json.cpp     AST -> JSON
src/main.cpp     CLI
web/             playground (server.py + index.html + app.js)
viz/             візуалізація AST без сервера
examples/        тестові програми
run_tests.sh     тести
```

## Збірка і запуск

Потрібно: flex, bison 3.x, g++ (C++17), python3.

```bash
make                  # збірка
make test             # запуск усіх прикладів
make serve            # playground на http://localhost:8000
```

CLI:

```bash
./cppparser file.cpp --run              # виконати
./cppparser file.cpp --gen out.py       # згенерувати Python
./cppparser file.cpp --ast out.json     # AST у JSON
./cppparser file.cpp --viz viz/ast.js   # AST для viz/index.html
./cppparser file.cpp --no-sema          # без семантичної перевірки
```

Коди завершення: 0 — ок, 2 — синтаксична помилка, 4 — семантичні помилки, 3 — помилка виконання.

## Playground

`make serve` → http://localhost:8000. Зліва редактор (приклади зі списку або свій код), поле stdin для `cin`. Справа вкладки: вивід інтерпретатора поряд із виводом згенерованого Python і чи збігаються; AST (згортання кліком, зум); Python-код; повідомлення парсера й семантичного аналізу. Рядки з помилками підсвічуються в редакторі. `web/server.py` — `http.server` зі стандартної бібліотеки, запускає `cppparser` і `python3` з таймаутом 5 с. d3.js лежить локально.

## Підтримувана підмножина

- `int, double, bool, char, string, void`, класи
- `#include`, `using namespace std;`, коментарі
- змінні `int a, b = 1;`, масиви `int a[5] = {1,2,3};`, об'єкти `P p(1, 2);`
- функції, рекурсія, прототипи
- класи: поля, перевантажені конструктори, списки ініціалізації `: Base(a), x(b)`, методи в класі й поза ним (`T C::f() {}`), `this->`, одиночне спадкування, `public/private`
- `if / else if / else`, `while`, `do-while`, `for`, `break`, `continue`, `return`
- арифметика, порівняння, `&& || !`, `?:`, `= += -= *= /= %=`, `++ --`, `(int)x`, індексація, `.` `->`, виклики
- `cout << … << endl;`, `cin >> x;`, `sqrt pow abs max min to_string`, `s.length()`

Немає: вказівників, шаблонів, `new/delete`, `switch`, посилань (`int&` парситься, але передається за значенням). Усі методи віртуальні. Об'єкти копіюються за значенням, масиви — за посиланням. `P p();` — прототип функції (most vexing parse). Рекурсія до 50000 викликів.

## Приклади

- `arith.cpp` — арифметика, пріоритети
- `shapes.cpp` — класи, спадкування, методи поза класом, рекурсія

- `tricky.cpp` — dangling else, `a = b = c`, `i++` у виразах, затінення змінних у блоках, приведення типів, масив об'єктів, char-арифметика
- `bad.cpp` — синтаксична помилка
- `sema_errors.cpp` — 16 семантичних помилок

## Як працює

```
file.cpp → lexer.l → parser.y → AST → sema.cpp (помилки → стоп)
                                    → interp.cpp (виконання)
                                    → codegen.cpp (Python)
                                    → json.cpp (JSON для d3)
```

AST — однорідні вузли `Node { type, value, kids, line }`. Дії в правилах Bison лише будують дерево, вся семантика в окремих проходах.

Семантичний аналіз: збирає класи й функції, потім проходить тіла зі стеком областей видимості і виводить тип кожного виразу. Ловить неоголошені імена, повторні оголошення, невідомі типи/поля/методи, кількість і типи аргументів, несумісні типи, присвоєння не-lvalue, `break` поза циклом, `this` поза методом, `return` не того типу, функцію без `return` на якомусь шляху. Усі помилки збирає списком.

Інтерпретатор: `Value` з тегом типу, `Env` — стек областей + `this` + глобальні. `break/continue/return` через винятки. Тип змінної зберігається при присвоєнні (`int x = 7.9` → 7). Виконується у потоці зі стеком 1 ГБ.

Генератор Python: веде стек областей з типами змінних, тому `{ int x; }` у вкладеному блоці стає `x_2`, `int t = 7.9` → `int(7.9)`, параметри й `return` приводяться до оголошених типів. Ділення і остача через `_div`/`_mod` (семантика C). `for` → `while` (крок дублюється перед `continue`). `a = b = c` і `i++` у виразі → `:=`, для полів і елементів масиву — `_setattr/_incattr/_setitem/_incitem`. `char` — рядок з одного символу, в арифметиці обгортається в `_ord`. Масив об'єктів → `[P() for _ in range(n)]`. Кілька конструкторів → `__init__(self, *args)` з диспетчером за `len(args)`.

## Теорія

**LR-розбір.** Читає вхід зліва направо, будує правий вивід у зворотному порядку (знизу вгору). Стек + дві дії: shift (покласти токен) і reduce (згорнути праву частину правила в нетермінал). Стан автомата — множина пунктів `A → α • β`.

- LR(0): без lookahead, конфлікти майже завжди.
- SLR(1): reduce, якщо наступний токен ∈ FOLLOW(A). FOLLOW грубий — спільний для всієї граматики.
- LR(1): lookahead у кожному пункті. Точний, але дуже багато станів.
- LALR(1): стани LR(1) з однаковим ядром зливаються, lookahead об'єднуються. Станів як у SLR, точність майже як у LR(1). При злитті можуть з'явитися нові reduce/reduce конфлікти (shift/reduce — ні). Bison за замовчуванням будує LALR(1).

Таблиця: `ACTION[стан, термінал]` = shift/reduce/accept/error, `GOTO[стан, нетермінал]`. У проєкті ~90 правил, 302 стани (`build/parser.output` після `bison -v`), 0 конфліктів.

**Bison.** На вході `.y`: токени, пріоритети (`%left %right %nonassoc`), `%union`, правила з діями. Bison додає `$accept → program $end`, будує LR(0)-автомат, рахує lookahead, будує таблиці, генерує `yyparse()`. `yyparse()` в циклі читає токени з `yylex()` (Flex), значення через `yylval`, позиції через `yylloc`. Дії виконуються на reduce: `$$` — ліва частина, `$1..$n` — права. При помилці — `yyerror()`; `%define parse.error verbose` дає «unexpected X, expecting Y».

**Shift/reduce.** У стані можна і зсунути токен, і згорнути правило. За замовчуванням Bison робить shift. Керується пріоритетами: токену — через `%left/%right/%nonassoc` (чим нижче в файлі, тим вищий), правилу — пріоритет останнього терміналу або явно `%prec`. Токен вищий → shift, нижчий → reduce, рівні: `%left` → reduce, `%right` → shift, `%nonassoc` → помилка.

У проєкті:
- `expr '+' expr • '*'` → shift (`*` вищий) → `2 + (3*4)`; `expr '+' expr • '+'` → reduce (`%left`) → ліва асоціативність; `a = b = c` → `%right` → права.
- dangling else: `IF '(' expr ')' stmt •` при `ELSE` — reduce або shift. `%nonassoc LOWER_THAN_ELSE` нижче, `%nonassoc ELSE` вище, коротке правило з `%prec LOWER_THAN_ELSE` → shift, `else` прив'язується до найближчого `if`.
- префіксні `++`/`--` з `%prec PREFIX` нижче за `[` і `.` → `++a[2]` = `++(a[2])`.

**Reduce/reduce.** Два правила можна згорнути при одному lookahead. Bison бере те, що раніше в граматиці, пріоритети не допомагають — треба переписувати граматику. У проєкті був: `P p();` — об'єкт з порожніми аргументами (`args → ε`) чи прототип функції (`params → ε`)? Після `(` з lookahead `)` неясно, яке ε згортати. Стандарт C++ каже, що це функція (most vexing parse), тому для об'єкта аргументи зроблено непорожніми — конфлікт зник.

Діагностика: `bison -v` (`parser.output`), `bison -Wcounterexamples` (показує два варіанти розбору).

**Чому повний C++ не LALR(1).** `a * b;` — множення чи оголошення вказівника залежить від того, чи `a` тип; `A<B, C> d;` — шаблон чи два порівняння. Потрібна таблиця символів під час розбору. GCC/Clang використовують рекурсивний спуск. Тут вказівники й шаблони прибрано, а `тип змінна` автомат розрізняє сам: після `IDENT` lookahead `IDENT` → тип, інакше вираз.
